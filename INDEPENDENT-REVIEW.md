## 3. Сложность для вайбкодера «с нуля»

### 3.1. Разбивка по подсистемам

| Подсистема | Сложность | Почему именно так |
|---|---:|---|
| Лендинг, дизайн-система, тёмная тема | 3 | Рутина, ИИ делает почти всё |
| Расписание + ДЗ + загрузка файлов | 6 | Много бизнес-правил (дедлайны, классы, роли), но всё детерминировано |
| Мультиарендность (школы) + RBAC | **9** | Каждый запрос, страница, сокет и файл обязаны фильтроваться по `schoolId`; ошибка = утечка между школами |
| NextAuth с fail-closed JWT | **9** | Роль/бан/версия сессии только из БД, отзыв токенов, сверка раз в 60 с, `SessionRevokedError` — это уровень «синьор+» |
| Socket.IO: auth handshake, origin-check, комнаты, лимиты | 8 | Легко получить cross-site WebSocket hijacking или «подслушивание» чужой комнаты |
| WebRTC mesh + TURN/relay + реконнект | **9** | Самая капризная часть: NAT, VPN, мобильные сети, ICE-restart |
| Доска Fabric.js + синхронизация + undo/redo + страницы | 8 | Конфликты состояния, сериализация, лимиты, снапшоты |
| ИИ-цепочка с fallback + Vision + JSON-чертежи + LaTeX | 7 | Много внешних API, таймаутов, форматов ответа |
| Админ-панель (метрики, аудит, живые комнаты) | 5 | Много UI, но логика простая |
| PWA + Android APK + Electron + DMG + EXE + подписи | 8 | Пять платформ, подпись, Gatekeeper, Gradle, CI |
| Шифрование чата (AES-CBC + HMAC, derive keys) | 7 | Легко сделать небезопасно (CBC без MAC, переиспользование IV) |

### 3.2. Реалистичные сроки

| Сценарий | Оценка |
|---|---|
| Один сильный разработчик с ИИ, «сделать работающее» | **10–14 недель** fulltime |
| Один сильный разработчик, «сделать безопасным и поддерживаемым» | **4–6 месяцев** |
| Вайбкодер без опыта в auth/multi-tenancy | 8–12 недель до демо, но с гарантированными дырами в правах доступа; правки займут ещё столько же |
| Команда 2–3 человека | 6–8 недель |

Для сравнения: типовой «вайб-проект» (лендинг + CRUD + авторизация по email) — это 3/10 по этой шкале. Здесь — **8.5/10**: примерно 5 продуктов в одном (LMS, видеоконференция, интерактивная доска, админка школы, мультиплатформенная оболочка).

### 3.3. Где вайбкодер ломается чаще всего (и где этот проект почти не сломался)

1. **Проверка прав на каждом уровне.** Типичная ошибка — «защитил страницу в layout и успокоился». Здесь это сделано правильно: `middleware` + `requireViewer/requireSchoolViewer/requireAdminViewer` + повторная живая проверка админа из БД (`src/lib/session-viewer.ts`). Из 34 роутов без гарда остались только три — и все три публичные по смыслу (`/api/auth/*`, `/api/schools/check`).
2. **Доверие JWT.** Классика — «роль в токене навсегда». Здесь роль, школа, класс и бан перечитываются из БД, а расхождение `sessionVersion` аннулирует сессию (`src/lib/auth-token.ts`). Это редкий и правильный паттерн.
3. **Проверка размера/типа файла после буферизации.** Ломается и здесь: см. §4.4.
4. **Секреты «для демо» в публичном репозитории.** Ломается здесь, см. §4.1 — это главная проблема проекта.

## 4. Безопасность

### 4.1. P0 — Критично: деплой по умолчанию можно захватить в админа

Три вещи складываются в один эксплойт:

1. В публичном репозитории лежат **демо-пароли гарантированных админов** (`src/lib/school-config.ts:145–165`). При старте `provisionConfiguredSchools()` (`server.ts:22`, `src/lib/schools.ts:319`) создаёт эти аккаунты, если их нет — то есть на **любом свежем деплое** они есть.
2. Там же лежат **детерминированные admin-invite-токены** (`src/lib/school-config.ts:104–108`). При создании школы они записываются в БД как есть (`inviteTokensForNewSchool` → `adminInviteTokenFor`), а `POST /api/auth/register` с этими токенами **выдаёт роль `ADMIN`** (`src/lib/invite-rules.ts`, `rolesForInvite`).
3. `AUDIT.md` помечает C-01/C-02 как `[FIXED]`. Фактически закрыт только один вектор: provisioning больше **не перетирает** уже сменённый пароль и не откатывает ротированный токен. Сами значения остались значениями по умолчанию — и на новом деплое они валидны.

**Условие эксплуатации:** оператор не задал `SCHOOLMEET_DEMO_ADMIN_PASSWORDS` и `SCHOOLMEET_ADMIN_INVITE_TOKENS`. Для `*.onrender.com`-деплоя из `electron-app/main.js` это надо проверить прямо сейчас.

**Что сделать (сегодня):**
- Задать обе переменные случайными значениями (32+ символа, `openssl rand -base64 32`).
- Ротировать пароли трёх админов через админку/БД, проверить `AuditLog` на чужие входы и повышения роли.
- Лучше — вообще убрать литералы из кода: генерировать пароль при первом создании и печатать **один раз** в лог/секрет-хранилище, а токены — только `randomUUID()`.
- Проверить регрессионным тестом, что без env `GUARANTEED_ADMINS[*].password` — не константа.

Дополнительно: `ensureGuaranteedAdmin` при каждом старте **снимает бан** (`isBanned: false`) и возвращает роль `ADMIN` (`src/lib/schools.ts:140–187`). То есть забаненный (или понижённый) демо-админ «воскресает» после рестарта — это уже не только про пароли.

### 4.3. Medium

- **PII в логах**: `console.log('[AUTH] Login attempt for: <email>')` и `[AUTH_FAIL] User not found` пишут email открытым текстом в каждый лог (`src/lib/auth.ts:179`). Для школьного продукта — это персональные данные несовершеннолетних в логах хостинга.
- **Шифрование чата — не E2E и почти не даёт защиты**: ключ хранится в `Meeting.encryptionKey` в той же БД и выдаётся любому допущенному клиенту. При утечке дампа сообщения читаются одним SQL-запросом. В README это честно оговорено, но «AES-256» в лендинге/доках читается пользователями как «сквозное». AES-CBC + HMAC реализован корректно (encrypt-then-MAC, случайный IV, constant-time сравнение) — претензий к примитивам нет.
- **Коды комнат человекочитаемые и предсказуемые** (`matematika-8b`), а `/api/meetings/[code]` различает «нет комнаты» (404) и «комната есть, но чужая» (403) — возможна разведка существующих уроков внутри школы. Для строгих школ ущерб ограничен, для гибких любой ученик школы входит в любой урок — это осознанная политика, но её стоит явно писать в UI.
- **Endpoint `/api/schools/check`** без сессии и без собственного лимита: создаёт школы/классы и досыпает токены. Сам по себе не выдаёт секретов (проверено), но это состояние-меняющий публичный GET/POST — лучше сделать его read-only и идемпотентным без записи.
- **`formData()` буферизует всё тело до проверки размера** (`src/app/api/homework/[id]/files/route.ts:26–36`): комментарий утверждает «проверяем размер до чтения тела», но `await request.formData()` уже прочитал его целиком в память. 512 МБ процесса → достаточно нескольких параллельных загрузок, чтобы получить OOM. Нужен `Content-Length`-гейт и/или стриминговый парсер.
- **`public/eduflow.dmg` — не приложение, а 56 КБ shell-скрипт**, открывающий сайт в Safari (`scripts/create-mac-dmg.py`). Это легитимный «browser launcher», но кнопка «Скачать для Mac» на лендинге воспринимается как нативное приложение. APK — тоже WebView-обёртка (149 КБ). Честная формулировка на лендинге обязательна.

### 4.4. Что сделано реально хорошо (не для галочки)

- `resolveMeetingAccess` — **одно** правило доступа для HTTP-страницы, API и `join-room`; логика не «дрейфует» между транспортами (`src/lib/meeting-access.ts`).
- Проверка `Origin` при апгрейде WebSocket (`isAllowedOrigin`) — закрывает cross-site WebSocket hijacking.
- `resolveStoragePath` — жёсткая проверка имени файла + `path.dirname(target) === dir`: path traversal невозможен, имена на диске генерирует сервер (UUID).
- Проверка файла **по трём признакам**: расширение, MIME и сигнатура первых байт. Переименованный `.exe` в `.pdf` не пройдёт.
- Класс-код допуска — подписанный HMAC-грант с привязкой к пользователю, классу, комнате и часом жизни (`src/lib/class-code.ts`). Это заметно лучше «пароля на урок».
- Electron: `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, белый список URL, `setPermissionRequestHandler`. Android: `allowFileAccess=false`, `MIXED_CONTENT_NEVER_ALLOW`, `usesCleartextTraffic=false`, мост из трёх безобидных методов. Обёртки сделаны аккуратно.
- Prisma: `connection_limit=10` + авто-переключение на `-pooler` для Neon — типичная ошибка «упёрлись в лимит соединений» здесь предусмотрена.
- ИИ-панель закрыта на сервере (`requireRole`), concurrency-cap 4, лимиты промпта и изображения.
- Все изменения ролей/бана/объявлений пишутся в `AuditLog` с IP.

## 5. Оптимизация

### 5.1. Что уже хорошо

- **32 индекса** в схеме под реальные запросы (`schoolId+classId+dayOfWeek`, `schoolId+isActive+createdAt` и т.д.).

## 6. Надёжность и эксплуатация

### 6.1. Что мешает спать спокойно

1. **Нет CI для веб-приложения.** В `.github/workflows` четыре воркфлоу: Android build, Android emulator smoke, macOS DMG, Windows installer. Ни один не запускает `npm test`, `tsc --noEmit`, `next build` или `npm audit`. Все 447 проверок существуют, но **ни один PR их не проверяет** — регресс пройдёт молча. Это самый дешёвый в исправлении и самый дорогой по последствиям пункт.
2. **Тесты в основном статические.** В `scripts/ui-patterns.test.ts` — 154 обращения к `readFileSync`/`REPO_ROOT`: тесты проверяют, что в исходнике есть определённая строка/класс/атрибут. Это ловит случайное удаление `aria-label`, но не ловит ни одну ошибку прав доступа. **Нет ни одного теста, который поднимает БД и дергает реальный API** (проверка «ученик другой школы получает 404» — самая ценная из всех и её нет). `test:ai` (103 проверки) сделан правильно — внешние API подменяются через внедряемый `fetch`, сеть не нужна, — но и он проверяет только слой ИИ.
3. **Нет миграций.** `db:push` = `prisma db push`, истории миграций нет вообще (`prisma/migrations` отсутствует). Для школьной БД с оценками и ДЗ это означает: изменить схему безопасно нельзя, откат невозможен. Переход на `prisma migrate` — обязателен до первых реальных пользователей.
4. **Файлы ДЗ — на локальном диске** (`UPLOAD_DIR=./storage/uploads`). На Vercel диск эфемерный (файлы исчезают), на Render — исчезают при каждом редеплое. `.env.example` это признаёт, но код продакшена от этого не защищён. Нужен S3/R2 + подписанные URL.
5. **Single point of failure.** В памяти процесса: комнаты, доска, закреплённые сообщения, счётчики участников, rate-limit, кэши. Падение/рестарт = потеря досок, «зависшие» записи посещаемости (`leftAt = null` навсегда) и сброс всех лимитов. Функции восстановления «забытых» attendance-записей при старте нет.
6. **Нет health-check, метрик и трекинга ошибок.** Только `console.error`. Для школьного продукта, где «не работает звонок у 5-Б» — это инцидент, нужен Sentry/OpenTelemetry + `/api/health` (БД + сокеты) для Render/Vercel.
7. **`/api/ai` с `maxDuration = 60`** на Hobby-плане Vercel упирается в лимит платформы; при таймауте пользователь получает 504 без внятного сообщения.
8. **Деплой на Vercel и кастомный `server.ts` несовместимы.** `attachRealtime` работает только там, где живёт долгоживущий Node-процесс. В репозитории одновременно `vercel.json` и `server.ts` — нужно явно зафиксировать: **realtime только на Render/своём VPS**, Vercel — только как статика/API. Сейчас эта двусмысленность в доках есть, в коде — нет.

### 6.2. Что сделано для отказоустойчивости

- Каждая секция дашборда изолирована: падение БД → пустые данные + баннер деградации, а не экран ошибки (`src/lib/dashboard-data.ts`).
- 5 `error.tsx` и 5 `loading.tsx` — сегментные границы есть там, где нужно.
- `handleRouteError` не отдаёт наружу стектрейсы и маппит Prisma-гонки в `409`.
- `withRoomLock` сериализует join/end/leave — состояние комнаты не «воскресает» после завершения урока.
- Идемпотентный provisioning и бэкфиллы (запускаются повторно без вреда).

## 7. Итоговые оценки и как их читать

### Сложность — 8.5/10
Пять платформ, realtime-видео, совместная доска, ИИ с Vision, мультиарендность и RBAC. Это работа на 3–6 месяцев для одного человека; вайбкодер дойдёт до «работает на демо» за 2–3 месяца, но без отдельного этапа «security review» получит дыры в правах — что и подтверждает история проекта (аудит нашёл 2 critical + 6 high).

### Оптимизация — 6.5/10
Плюсы: индексы, кэши с TTL, батчи, транзакции, лимиты на всё (чат, доска, ИИ, загрузки), `connection_limit` под Neon.
Минусы: 3–4 запроса на аутентификацию в каждом вызове, полный снапшот доски, память как единственное хранилище состояния, отсутствие Redis, 96 МБ артефакт в бандле публичной папки.

### Безопасность — 5/10
Плюсы: продуманная модель доступа (middleware + живые проверки из БД + capability), отзыв JWT по `sessionVersion`, единая функция `resolveMeetingAccess` для HTTP и сокетов, HMAC-гранты, защита путей и сигнатур файлов, аккуратные Electron/Android-обёртки.
Минусы: **дефолтный админ-доступ в публичном репо (P0)**, отсутствие security-заголовков, EOL Next.js с critical advisory, обходимый rate-limit, отсутствие подтверждения email/сброса пароля, публичный TURN с общими кредами.
Без P0 оценка была бы 7/10. С ним — 5/10, потому что это не «теоретическая» уязвимость, а готовый вход в админку на свежем деплое.

### Надёжность — 6/10
Плюсы: graceful degradation, идемпотентность, таймауты, обработка гонок, error boundaries, подробная документация деплоя.
Минусы: нет CI на веб, нет миграций, нет объектного хранилища, состояние в памяти, нет health-check/мониторинга, эфемерная файловая система.

## 8. План на ближайшие 2 недели (по убыванию отношения «эффект / трудозатраты»)

**День 1 — закрыть P0 (2–3 часа)**
1. Задать `SCHOOLMEET_DEMO_ADMIN_PASSWORDS` и `SCHOOLMEET_ADMIN_INVITE_TOKENS` случайными значениями; ротировать пароли админов.
2. Проверить `AuditLog` на `user.role.change` и подозрительные входы.
3. Убрать литеральные пароли/токены из `school-config.ts` (оставить только env; без env — генерировать случайно и логировать один раз).

**Неделя 1 — «чтобы не взломали и не потеряли данные»**
4. Security-заголовки в `next.config.mjs`: CSP (с `frame-ancestors 'none'`), HSTS, `Referrer-Policy`, `Permissions-Policy: camera=(self), microphone=(self)`.
5. Обновить Next.js до поддерживаемой мажорной версии (это `H-04` из старого аудита — единственная «отложенная» находка, её нельзя тянуть дальше).
6. CI-workflow `ci.yml`: `npm ci` → `tsc --noEmit` → `npm test` → `npm run build` → `npm audit --audit-level=high` на каждый PR.
7. Перейти на `prisma migrate` (baseline-миграция + `migrate deploy` в деплое).
8. Индекс `homework_submissions(studentId)`.

**Неделя 2 — «чтобы не падало и масштабировалось»**
9. S3/R2 для файлов ДЗ + подписанные ссылки.
10. Сократить auth-оверхед: один запрос с join'ом вместо `ensureUserSchoolMembership` + `findUnique`; кэш зрителя на время запроса.
11. Добавить хотя бы 10 интеграционных тестов на API с реальной БД (изоляция школ, доступ к чужому уроку, загрузка файла, повышение роли).
12. `/api/health` + Sentry (или аналог).
13. Ограничить размер снапшота доски и ввести TTL/лимит памяти на комнату; `Content-Length`-гейт перед `formData()`.
14. Убрать `public/eduflow-setup.exe` в Releases; на лендинге честно назвать `.dmg`/`.apk` «веб-обёрткой».

## 9. Вердикт

Это **сильный инженерный артефакт** с редкой для «вайб-проектов» дисциплиной: строгий TypeScript, ноль `any`, осмысленные комментарии, 447 тестовых проверок, продуманная модель прав, аккуратные обёртки под Android/Electron и документация на 7.5 тыс. слов. По сложности — **8.5/10**, это полноценный мультиплатформенный продукт, а не упражнение.

Но проект находится в опасной точке: **он выглядит готовым к продакшену сильнее, чем является**. Критическая дыра с админ-доступом по умолчанию — не гипотетическая, она срабатывает на каждом свежем деплое, где оператор не переопределил env; отсутствие CI означает, что 447 зелёных проверок ничего не гарантируют при следующем PR; отсутствие миграций и объектного хранилища означает, что первые же реальные пользователи создадут невосстановимые данные.

Хорошая новость: **все P0/P1 закрываются за 1–2 недели**, потому что архитектура под них уже правильная. Это редкость — обычно в таких проектах чинить нужно не конфиг, а всю модель доступа.

**Итог: 6.7/10 сейчас, 8.5/10 после плана из §8.**
