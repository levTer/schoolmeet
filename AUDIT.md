# Глобальный аудит EduFlow 360°

**Бренд:** EduFlow (до ребрендинга — SchoolMeet); технические идентификаторы в отчёте приведены в исходном виде.<br>
**Дата:** 2026-10-16<br>
**Обновление (статус исправлений):** 2026-10-17 — Critical и High закрыты в PR «security: fix critical multi-tenancy leaks, meeting authorization, and JWT fail-closed logic» (кроме H-04, требующей major-обновления Next.js; см. статус у находки).<br>
**Объём:** безопасность, tenant isolation, производительность, код и зависимости, UX/accessibility, целостность БД, ИИ, WebSocket/realtime, тесты и архитектура.<br>
**Итоговая оценка:** **4/10** — среднее арифметическое оценок десяти направлений ниже.<br>

> Секретные значения из исходников и документации в отчёте намеренно не повторяются. Репозиторий [`levTer/schoolmeet`](https://github.com/levTer/schoolmeet) публичный; это существенно для оценки найденных в нём паролей и invite-токенов.

## Краткий вывод

В проекте есть хорошие базовые механизмы: bcrypt для паролей, серверная проверка роли и школы в большинстве учебных API, tenant namespace в Socket.IO, ограничения частоты для чата/доски, ручное подтверждение ИИ-оценки учителем. При этом найдены два критических пути к роли `ADMIN`: опубликованные invite-токены и жёстко заданные учётные записи, которые приложение восстанавливает при инициализации. Также выявлены fail-open ветка обновления JWT, отсутствие проверки класса при входе в scheduled meeting, межшкольная видимость объявлений и неоднозначный контракт роли администратора в multi-tenant системе.

Главные практические риски: компрометация админ-доступа; доступ к урокам другого класса той же школы; неконсистентное разделение данных между школами; устаревшие/уязвимые зависимости; зависимость безопасности и realtime от одного процесса и его памяти.

### Critical

#### [FIXED] C-01. Статические admin invite-токены позволяют повысить аккаунт до `ADMIN`

- Литералы admin-токенов находятся в публичном репозитории: [`src/lib/school-config.ts:20–32`](src/lib/school-config.ts#L20). Они используются при восстановлении invite-значения в БД: [`src/lib/invite-tokens.ts:69–78`](src/lib/invite-tokens.ts#L69).
- Публичный endpoint проверки школы вызывает код, который для настроенных школ сбрасывает хранимый admin-токен к preset-значению: [`src/app/api/schools/check/route.ts:93–109`](src/app/api/schools/check/route.ts#L93). **Endpoint не возвращает токен в JSON**, но публичный исходный код уже раскрывает его, а запрос мешает надёжно заменить его только в БД.
- Повышение требует только авторизованного пользователя, подходящей школы и совпадающего токена; затем роль меняется на `ADMIN`: [`src/app/api/auth/promote/route.ts:41–55, 58–85`](src/app/api/auth/promote/route.ts#L41).
- Роль `ADMIN` описана в схеме как имеющая доступ ко всем данным платформы: [`prisma/schema.prisma:15–17`](prisma/schema.prisma#L15).

**Воздействие:** зарегистрированный пользователь, имеющий доступ к публичному исходному коду, может получить глобальные admin-права.

**Рекомендация:** немедленно отозвать все опубликованные значения; выдавать новые случайные одноразовые токены вне репозитория, хранить/валидировать их безопасно и не восстанавливать фиксированный токен из публичного endpoint или startup provisioning.
**Статус [FIXED] (2026-10-17):**
- Публичный `/api/schools/check` и startup-provisioning больше НЕ возвращают предустановленный admin-токен: оба пути переведены на `provisioningInviteData()` (`src/lib/invite-tokens.ts`), который досыпает только отсутствующие значения. Ротация секрета в БД теперь сохраняется.
- Возврат к литералу из репозитория возможен только по явному флагу оператора `SCHOOLMEET_RESTORE_CONFIGURED_INVITE_TOKENS=true` (однократная процедура), по умолчанию выключен.
- Значение токена задаётся переменной `SCHOOLMEET_ADMIN_INVITE_TOKENS` (JSON «код школы → токен») и имеет приоритет над демо-литералами; демо-литералы оставлены только для «работы из коробки» и для тестов.
- Endpoint проверки школы по-прежнему не отдаёт токены в JSON (добавлена регрессионная проверка), уровень ссылки (`inviteRole`) считается на сервере.
- Регрессионные тесты: `scripts/security-rules.test.ts` → «C-01: публичная инициализация не возвращает известный admin-токен».
- **Остаётся за оператором:** задать `SCHOOLMEET_ADMIN_INVITE_TOKENS` в продакшене (ротация опубликованных значений).


#### [FIXED] C-02. Известные bootstrap-пароли администратора восстанавливаются при инициализации

- Данные гарантированных администраторов содержат статические пароли: [`src/lib/school-config.ts:36–69`](src/lib/school-config.ts#L36). Provisioning каждый раз формирует из них новый bcrypt-хеш и обновляет запись: [`src/lib/schools.ts:128–161`](src/lib/schools.ts#L128); startup вызывает provisioning: [`server.ts:22–28`](server.ts#L22).
- Эти реквизиты также опубликованы в README и инструкции deployment: [`README.md:186–203`](README.md#L186), [`DEPLOYMENT.md:243–267`](DEPLOYMENT.md#L243). Значения намеренно не перепечатаны здесь.
- Seed использует общий пароль по умолчанию и выводит данные доступа в лог: [`prisma/seed.ts:25, 137–161, 444–450`](prisma/seed.ts#L25).

**Воздействие:** смена пароля через интерфейс не является постоянной — следующий запуск может вернуть известный пароль; публичный README/source раскрывает доступ к аккаунтам.

**Рекомендация:** удалить статические credentials из репозитория и публичных документов; создавать bootstrap-admin только при явной одноразовой настройке через секретное окружение, не сбрасывать пароль на каждом запуске, ротировать все раскрытые credentials и проверить логи deployment.
**Статус [FIXED] (2026-10-17):**
- `ensureGuaranteedAdmin` (`src/lib/schools.ts`) теперь создаёт аккаунт, только если его НЕТ; у существующего аккаунта обновляются имя, роль, школа и снятие блокировки, а пароль **не перетирается**. Смена пароля через админ-панель больше не отменяется следующим стартом.
- Принудительный возврат демо-пароля — только по разовому флагу `SCHOOLMEET_RESET_DEMO_ADMIN_PASSWORDS=true`; автосоздание полностью отключается `SCHOOLMEET_DISABLE_DEMO_ADMIN_SEED=true`.
- Пароли задаются переменной `SCHOOLMEET_DEMO_ADMIN_PASSWORDS` (JSON «email → пароль»); литералы в репозитории остаются демо-значениями, которые в продуктиве переопределяются окружением.
- Пароли больше не печатаются в логах: `prisma/seed.ts` и provisioning логируют только email/роль.
- Из `README.md` и `DEPLOYMENT.md` удалены таблицы с паролями (`Admin123!` и др.) — вместо них описание переменных окружения; это же проверяется тестом.
- Хеширование осталось bcrypt (10 раундов), открытый пароль никуда не сохраняется и не возвращается API.
- **Остаётся за оператором:** задать свои пароли через `SCHOOLMEET_DEMO_ADMIN_PASSWORDS` и/или отключить автосоздание, а также проверить логи предыдущих деплоев на раскрытые реквизиты.


### High

#### [FIXED] H-01. Обновление сессии доверяет присланной клиентом роли, если сверка с БД падает

В JWT callback при `trigger === "update"` значение `session.user.role` копируется в токен **до** запроса к БД: [`src/lib/auth.ts:207–228`](src/lib/auth.ts#L207). Если запрос не проходит, ошибка только логируется; прежнее значение не откатывается, а `token.syncedAt` всё равно обновляется: [`src/lib/auth.ts:235–265`](src/lib/auth.ts#L235). Админ-страница пользователей проверяет роль из сессии и сразу загружает список, не вызывая live `requireViewer`: [`src/app/admin/users/page.tsx:25–33`](src/app/admin/users/page.tsx#L25).

**Условие эксплуатации:** авторизованный пользователь отправляет поддерживаемое NextAuth обновление своей сессии с `role: "ADMIN"` в момент ошибки чтения пользователя из БД; если БД восстановится в течение окна синхронизации, сессия может быть принята админ-страницами со старым/поддельным claim. API, использующие `requireViewer`, дополнительно сверяют роль с БД, но это не защищает описанную server-rendered страницу.

**Рекомендация:** игнорировать роль/школу из update payload; при невозможности авторитетной сверки не выдавать обновлённый привилегированный токен; не обновлять `syncedAt` после ошибки; добавить regression-тест на NextAuth callback и страницу.
**Статус [FIXED] (2026-10-17):**
- Логика вынесена в чистый модуль `src/lib/auth-token.ts`: клиентские claims (`role`, `schoolId`, `classId`, `schoolName`, `banned`, `sessionVersion`) объявлены недоверенными и **никогда не копируются** в токен (список `UNTRUSTED_SESSION_FIELDS`). `trigger === "update"` теперь лишь принудительно запускает перечитывание из БД.
- Источник привилегий — только БД (`loadUserForSession`): роль, школа, класс, бан и версия сессии. JWT собирается функцией `applyDatabaseSnapshot`.
- Fail-closed: удалённый, заблокированный пользователь или расхождение версии сессии → `SessionRevokedError`; NextAuth чистит session-cookie и `getServerSession` возвращает `null`. При недоступной БД `syncedAt` не сдвигается, а токен с неподтверждёнными правами аннулируется; подтверждённый токен живёт не дольше `SESSION_SYNC_GRACE_MS` (24 ч).
- `session`-callback не выдаёт роль/школу/класс, если токен не авторитетен (нет `syncedAt`) — по умолчанию `STUDENT` и `schoolId: null`.
- Страницы `/admin` (layout) и `/admin/users` дополнительно подтверждают роль «живой» записью из БД (`getLiveAdminViewer`); при недоступной БД доступ в админку закрыт.
- Регрессионные тесты: `scripts/security-rules.test.ts` → «H-01: JWT доверяет только БД» (включая проверку самих админ-страниц).


#### [FIXED] H-02. Scheduled meeting можно открыть ученику другого класса той же школы

HTTP endpoint выдаёт `encryptionKey`, проверив школу, но не класс: [`src/app/api/meetings/[code]/route.ts:35–58`](src/app/api/meetings/%5Bcode%5D/route.ts#L35). Запрос meeting также загружает из schedule только `schoolId`, а не `classId`: [`src/lib/meetings.ts:47–53`](src/lib/meetings.ts#L47). Socket `join-room` подтверждает school membership, но не сравнивает класс участника с классом расписания: [`src/server/realtime.ts:612–626`](src/server/realtime.ts#L612).

**Воздействие:** ученик, знающий/угадавший код scheduled meeting, может получить ключ и войти в комнату другого класса своей школы. Это расходится с фильтрацией расписания учеников по классу. Межшкольный доступ в проверенном join path, напротив, ограничивается школой.

**Рекомендация:** для meeting, связанного с расписанием, сверять `viewer.classId` и `schedule.classId` и в HTTP, и в socket; не отдавать ключ до успешной проверки; отдельно определить доступ для внеплановых общешкольных встреч.
**Статус [FIXED] (2026-10-17):**
- Единое правило доступа вынесено в чистый модуль `src/lib/meeting-access.ts` (`resolveMeetingAccess`): школа урока обязана совпадать со школой зрителя (иначе `404 SCHOOL_MISMATCH`), а STUDENT обязан состоять в классе расписания урока (иначе `403 CLASS_FORBIDDEN`); TEACHER/ADMIN школы и ведущий урока проходят всегда. Внеплановые встречи без `schedule.classId` открыты всей школе.
- Проверка применяется до выдачи ключа: `GET /api/meetings/[code]` (ключ `encryptionKey` отдаётся только после `ok`), страница `/meeting/[id]` (отдельный экран «Вход в урок закрыт») и Socket.IO `join-room` — **до** входа в комнату, по классу из БД (`socket.data.user.classId` добавлен в handshake).
- `MeetingWithHost.schedule` теперь выбирает `classId`; `checkMeetingAccess()` в `src/lib/meetings.ts` — общая точка вызова для HTTP и сокета.
- Регрессионные тесты: `scripts/security-rules.test.ts` → «H-02: доступ к уроку ограничен школой и классом» + контракт `join-room`.


#### [FIXED] H-03. Объявления не изолированы по школе

Публичный для вошедших пользователей endpoint передаёт в выборку только `id`, `role`, `grade`, без `schoolId`; комментарий самого endpoint обещает ученику объявления его школы/класса: [`src/app/api/announcements/route.ts:9–22`](src/app/api/announcements/route.ts#L9). Модель `Announcement` хранит `targetGrade`, но не `schoolId`: [`prisma/schema.prisma:351–368`](prisma/schema.prisma#L351). Admin list/create/update/delete также оперируют объявлениями без tenant filter: [`src/lib/announcements.ts:159–172, 206–253`](src/lib/announcements.ts#L159).

**Воздействие:** активное объявление для класса/школы доступно пользователям других школ; администратор может управлять общим набором объявлений. Это не соответствует школьному назначению объявления в API/UI.

**Рекомендация:** добавить `schoolId` к модели и всем операциям/индексам; проверять принадлежность объявления школе зрителя на чтении, обновлении и удалении.
**Статус [FIXED] (2026-10-17):**
- Схема: `Announcement.schoolId String?` + связь `school School? @relation(... onDelete: Cascade)` + индекс `@@index([schoolId, isActive, createdAt])`; школа получила обратную связь `announcements`.

#### M-05. Whiteboard допускает большой объём памяти на одну активную комнату

Сервер допускает до 2 000 объектов и проверяет размер каждого через `JSON.stringify(...).length <= 64 KiB` (это UTF-16 code units, не byte length): [`src/lib/realtime.ts:25–34`](src/lib/realtime.ts#L25), [`src/server/realtime.ts:300–313, 354–356`](src/server/realtime.ts#L300). Номинальный предел serialized content для ASCII-объектов — около **125 MiB на комнату**, до учёта overhead JS-объектов; для escape/non-ASCII представления фактический heap может быть выше. `maxHttpBufferSize` ограничивает одно socket-событие, но не суммарный объём комнаты: [`src/server/realtime.ts:520–531`](src/server/realtime.ts#L520). **Рекомендация:** ограничить aggregate bytes на room, добавить idle TTL/eviction и тест на несколько комнат с крупными объектами.

#### L-02. Максимум пароля считается в символах, тогда как bcrypt обрезает по байтам

Лимит задокументирован как 72 байта, но проверка использует JavaScript `password.length`: [`src/lib/validation.ts:8–9, 171–180`](src/lib/validation.ts#L8). Для многобайтных Unicode-паролей bcrypt может игнорировать хвост после 72 UTF-8 байт, хотя UI принимает до 72 JS-символов.

**Рекомендация:** валидировать UTF-8 byte length или применять безопасное pre-hash решение с тестами на Unicode; сообщать пользователю фактическое ограничение.
